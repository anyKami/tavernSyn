# 增量同步核查与修复

日期：2026-10-26；基于 0.2.4 的未发布工作区修改。

## 核查结果

- 已复现：浅克隆产生的 Pack 名称变化，使 rsync 找不到同路径旧文件，新增很少内容仍可能重传整个 Pack。
- 已确认：原推送/拉取缺少完整的无变化快速路径，会继续复制、校验、准备依赖、应用和重启。
- 已确认：原拉取在没有 `cache/payload` 时从空目录开始，即使本机已有相近文件也不能复用。
- 进度口径：现有界面已经区分逻辑处理量与实际 rsync 收发量。本次进一步为无变化任务明确显示未启动文件传输。

## 修复

Git 插件继续使用单次提交的独立浅克隆，在暂存区将 Pack 展开为 Git 标准的 loose objects。未变化对象的哈希路径保持稳定，小提交不会再使同仓库的大对象随 Pack 改名一起重传。仓库编号由插件的便携路径确定，新增另一插件不会改变原插件的传输目录。保留原 `repositories/<数字>/gitdata` 结构、精简提交历史、分支、远端和工作文件，既有 VPS 协议无需变更。[Git 官方说明](https://git-scm.com/docs/git-unpack-objects)介绍了 Pack 到 loose objects 的转换及输入 Pack 必须移出可见对象库的原因。

完整本机状态摘要加入 Git 提交、分支、远端、共享配置与额外根标识。仅当已完成的本机同步基准、当前本机状态和经过再次核对的 VPS 内容摘要均一致，才走快速路径。推送仍先完成浏览器保存回执和等待页交接；跳过快照、rsync、发布和重启。拉取可直接跳过下载、候选插件依赖准备和应用。保存/版本检查期间有变化、首次同步、旧的不完整基准和待应用恢复任务均回到正常流程。

没有下载缓存时，只从已映射共享根中复制清单请求的对应文件作为差分基础，规范化设备保留 JSON 字段，排除本机运行代码、依赖和基础设施目录。临时副本的时间戳刻意与远端不同，使 rsync 比较块；随后仍进行逐文件 SHA-256 校验和必要的定向补传。不会直接把本机文件认定为已下载成功。

## 真实 rsync 对照实验

测试使用 2 MiB 随机二进制资源的 Git 插件，新增 19 B 文本并提交。旧方式保留浅克隆 Pack；新方式使用标准 loose objects。两组采用项目同一组 rsync 参数。

| 指标 | 旧方式 | 修复后 |
| --- | ---: | ---: |
| rsync 发送字节 | 2,100,375 | 3,121 |
| rsync 接收字节 | 307 | 9,084 |
| Literal data | 2,100,215 | 1,817 |
| Matched data | 405 | 2,099,140 |

数值为一次隔离运行，提交时间等会使少量字节波动；两组最终内容均通过校验，新 Git 目录也经实际恢复并核对 HEAD。不能据此保证所有插件更新都有相同压缩比。

无缓存下载实验从本机相近的 2 MiB 文件建立基础，使用 rsync 恢复远端内容：发送 4,193 B、接收 8,882 B，复用 2,094,608 B，最终完整校验通过。

## 验证与边界

- 增量修复初次验收为 109 项测试通过，无失败、无跳过。覆盖 Git 对象传输、稳定目录、Git/配置变更检测、保存与远端检查期间的变化、缺失的空额外目录、无变化跳过，以及缓存缺失时的基础复用。后续合并审查修复的回归见[审查修复记录](review-fixes.md)。
- 真实 SillyTavern 隔离环境 25 项检查通过，包含真实保存、等待页交接和无重启的推送/拉取快速路径；其传输适配器为内存实现。网络增量数值来自独立的真实 rsync 实验，不是实际 VPS 测量。
- 首次从旧 Pack 布局切换需建立一次新的 Git 对象基础。loose objects 会增加文件数量，也可能增加磁盘占用；被修改的大对象仍可能需要传输较多数据。
- 缓存缺失时复用的是本机共享工作文件，不能保证复用已经打包在本机 `.git` 内的全部传输对象。
- 无变化判断仍需要读取并核对内容，不是完全免磁盘 I/O；有变化的同步仍保留完整校验、覆盖确认、受控替换和恢复机制。
