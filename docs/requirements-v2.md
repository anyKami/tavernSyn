# SillyTavern 跨设备一键同步插件：完整项目需求 V2

## 1. 项目目标

为 SillyTavern（酒馆）开发一个跨平台同步插件，实现 Windows 电脑和 Android Termux 本地酒馆之间的数据及使用环境同步。

现有一台私人租用的 Linux VPS，已经加入 Tailscale 私有网络，作为唯一的同步存储中心。

两台设备各自运行本地 SillyTavern，不需要 VPS 承担聊天、模型请求或网页服务。

最终用户体验是：

**在酒馆界面点击「推送到 VPS」或「从 VPS 拉取」，完成增量同步。拉取后自动重启酒馆并恢复页面；无法自动重启时采用兼容降级方式。**

只使用 Git 仓库发布同步插件本身，不使用 Git 管理用户聊天和同步数据。

优先级：

1. 数据完整性和可靠性
2. 最大化跨设备的使用体验一致性
3. 操作简单
4. 增量同步效率
5. 基础安全保障
6. 低维护成本

避免过度设计。

## 2. 运行环境

### Windows

- Windows 10/11
- 本地 SillyTavern
- 可安装 rsync、OpenSSH、Git 等依赖
- 酒馆安装路径可配置
- 希望通过酒馆界面操作同步
- 支持自动关闭和重新启动酒馆

### Android

- Android 系统
- Termux 本地运行 SillyTavern
- 手机浏览器访问本地酒馆
- 可安装 rsync、OpenSSH、Git 等依赖
- Tailscale 客户端可访问 VPS 私网地址
- 尽量通过酒馆界面完成同步与重启

### VPS

- Debian/Ubuntu Linux
- 已部署 Tailscale
- 拥有 sudo/root 管理权限
- 使用专用同步账户和存储目录
- 不需要长期运行酒馆或额外 Web 服务
- 不得影响 VPS 以前部署酒馆留下的数据

必须支持自定义路径与 Tailscale 地址。

## 3. 插件整体架构

采用单一 Git 仓库，包含三个主要组件。

### A. UI Extension

运行在 SillyTavern 前端，负责：

- 在扩展设置界面展示同步面板
- 显示 VPS 连接状态
- 提供「推送到 VPS」按钮
- 提供「从 VPS 拉取」按钮
- 显示文件数量、实际传输量、进度和错误
- 提供首次配置引导
- 提供必要的覆盖确认
- 显示自动重启状态
- 在重启结束后尝试恢复连接和刷新页面

尽量使用 SillyTavern 官方提供的扩展 API。

### B. Server Plugin

运行在本地 SillyTavern Node.js 服务端，负责：

- 提供受保护的同步 API
- 管理本地同步任务
- 检查酒馆状态
- 触发保存操作与一致性检查
- 管理同步范围
- 检测插件清单及相关配置
- 调用 Sync Helper
- 提供同步状态查询
- 向 UI 报告进度与错误

不要让浏览器直接执行系统命令或访问 SSH 私钥。

所有高权限操作都必须由本地后端完成。

### C. Sync Helper

独立于 SillyTavern Node.js 进程的本机辅助组件。

职责：

- 执行 rsync 和 SSH
- 完成同步数据暂存
- 对即将应用的数据执行完整性检查
- 在必要时安全停止酒馆
- 替换或恢复相关文件
- 安装或修复必要的本机插件依赖
- 重新启动 SillyTavern
- 报告启动健康状态
- 处理无法自动重启的降级流程

Sync Helper 可以是轻量级 Node.js 程序或适当的平台脚本。

优先利用现有运行环境，不要默认增加常驻系统服务。

如果采用外部启动器或进程管理器，应确保首次配置以后日常无需操作终端。

## 4. 插件发布和安装

将 UI Extension、Server Plugin、Helper 和文档放入同一个 Git 仓库。

需要设计清晰的安装机制。

要求：

- Windows 与 Android 可以从同一仓库安装
- 兼容 SillyTavern 原生扩展与服务端插件机制
- 服务端插件启用方式清楚
- 同步插件自身可以独立更新
- 更新用户数据不得覆盖正在执行的同步程序
- 用户不必手动复制大量文件
- 插件安装失败或缺少依赖时给出明确说明

同步插件本身的代码、设备配置、任务状态和 SSH 凭据必须排除在普通用户数据镜像之外。

## 5. 同步方式

采用：

**rsync + SSH + Tailscale**

只提供两个核心操作：

### 推送（Push）

以当前设备为准，更新 VPS 数据。

- 对比本地和 VPS
- 增量传输修改的文件
- 同步新增和删除
- 完成后发布 VPS 最新有效数据
- 保留同步完成标记
- 报告同步结果

### 拉取（Pull）

以 VPS 为准，更新当前设备。

- 读取 VPS 最新有效数据
- 检查远程数据是否完整
- 增量下载数据
- 检查本机的未上传修改
- 必要时要求覆盖确认
- 将更新交给 Sync Helper 安全应用
- 完成后重新启动酒馆并恢复页面

不需要：

- Git 数据版本管理
- 多端自动合并
- 定时同步
- 多设备同时编辑同一个聊天的自动合并
- 复杂版本历史
- 自建数据库

用户主动决定上传或下载方向。

## 6. 完整数据同步范围

目标是尽可能恢复相同的酒馆使用环境，而不只是复制聊天记录。

### 共享用户数据

默认纳入：

- 全部聊天记录与聊天元数据
- 群聊记录和群组信息
- 角色卡及资源
- 世界书
- 预设
- 正则规则
- Quick Replies
- 用户人格和头像
- 图片和附件
- 用户自定义主题与 CSS
- 提示词模板
- API 连接配置
- API 密钥
- settings.json
- secrets.json
- 插件持久化设置
- 插件相关资源
- 其他可移植的用户数据

优先检查实际数据目录，避免遗漏扩展或插件产生的自定义数据。

### 插件代码与安装状态

当前环境主要有三类插件：

**第一类：通过 SillyTavern 界面使用 Git URL 安装的前端扩展。**

建议同步：

- 插件标识
- Git 仓库 URL
- 版本、分支或 commit
- 启用状态
- 持久化配置
- 相关资源数据

应评估是否需要通过原生安装机制在另一设备恢复代码，而不是直接覆盖 Git 元数据。

**第二类：使用 CDN 加载的前端脚本。**

建议同步：

- 脚本 URL
- 启用状态
- 加载参数
- 持久化设置
- 可固定的脚本版本

对于浏览器 localStorage、IndexedDB 内的特殊数据，应识别并记录限制。

第一版不要求全面复制浏览器数据库。

**第三类：通过 Git 安装的服务端插件。**

建议同步：

- 插件仓库及版本
- 可移植的源代码
- 配置及资源
- 持久化数据
- 启用状态

但必须考虑跨平台差异：

- node_modules 不直接跨平台镜像
- 原生 Node 模块分别安装
- 外部程序依赖分别检查
- 设备路径分别维护
- 不兼容配置需转换或保留本机版本

优先研究一种混合策略：

**插件安装清单 + 版本固定 + 可移植文件同步 + 本机依赖恢复。**

目标是尽可能保证两端插件一致，同时保留插件原有的安装和更新能力。

无法自动恢复的插件应显示明确原因，不能悄悄跳过后宣称完全同步。

## 7. 共享环境与设备差异

把数据分成三类。

### 共享层

跨设备同步的用户数据、角色卡、聊天、世界书、预设、插件设置、图片和密钥。

### 插件层

插件清单、代码版本、资源、可移植数据，以及平台依赖恢复状态。

### 设备层

保留在本机的：

- 网络监听地址
- 端口
- 设备绝对路径
- config.yaml 中不兼容的字段
- 设备级性能参数
- 窗口和屏幕专属配置
- SSH/Tailscale 身份信息
- 同步插件的本机连接配置
- 其他系统专属文件

对于 settings.json，不要简单地整体排除。

应设计可维护的配置字段保留策略，使大部分用户设置共享，少量设备专用值不被覆盖。

避免对未知 JSON 结构进行粗暴文本替换。

## 8. 拉取后自动重启

这是必须优先设计并验证的核心功能。

拉取流程：

1. 在 UI 中点击拉取。
2. 检查 VPS 状态。
3. 确定远程有效数据版本。
4. 增量下载到独立暂存区。
5. 完整性校验。
6. 检查覆盖风险。
7. 提示即将重启酒馆。
8. 将操作交给独立 Sync Helper。
9. 安全停止 SillyTavern。
10. 应用新的用户数据与插件变更。
11. 恢复设备专属设置。
12. 处理必要的本机插件依赖。
13. 重新启动酒馆。
14. 等待健康检查成功。
15. 刷新或恢复浏览器页面。
16. 展示同步完成状态。

### 自动重启要求

- 不能让负责重新启动的逻辑只存在于即将终止的酒馆进程中。
- 优先设计受控启动器。
- Windows 和 Android 分别提供进程管理适配。
- 不得无条件强制杀死进程。
- 重启前确认必要数据已经保存。
- 重启过程应可恢复。
- 同步状态不能只保存在前端页面内存中。

### 兼容降级

如果当前运行环境无法自动重启：

- 保留已经下载并验证的数据。
- 保留待应用状态。
- 明确提示用户如何重启。
- 下次通过受控启动方式启动时完成更新。
- 禁止在更新尚未应用时误报同步成功。

如果自动重启后健康检查失败，应尽量恢复更新前的必要数据或提供明确恢复步骤。

不要求复杂的全系统快照和历史回滚。

## 9. 推送时的数据一致性

需要认真处理正在运行的酒馆与文件同步之间的冲突。

设计时必须验证：

- 聊天消息何时落盘
- 角色与世界书修改何时保存
- settings.json 何时保存
- 插件设置何时保存
- 是否存在延迟写入
- 是否存在后台持续写入文件的插件

优先尝试调用官方提供的保存接口并确认完成。

如果无法保证完整目录在运行时的一致性，应设计安全的替代方案，例如由 Helper 进行短暂受控停机与同步后重启。

不得简单调用一次异步保存方法，就声称完成了一致性快照。

需要比较运行中推送与严格停机推送的可靠性、用户体验和性能，提出推荐默认方案。

## 10. VPS 数据存储设计

VPS 只保存同步镜像及少量状态信息。

必须考虑：

- 最新有效镜像
- 上传暂存目录
- 上传完成标记
- 同步排他锁
- 必要的恢复数据
- 同步状态元数据

上传过程中不能直接破坏已经发布的有效版本。

推荐：

1. 增量上传到暂存数据集。
2. 验证上传完整性。
3. 成功后原子发布最新镜像。
4. 失败时保留旧的有效镜像。
5. 清理不再需要的暂存数据。

可以评估硬链接或其他节省空间的机制，但需要确保修改暂存文件不会连带修改已发布版本。

拉取应绑定到一份稳定的有效镜像，不能读到两个不同上传批次混合的数据。

不需要复杂历史版本系统，只保留最低限度的恢复能力。

## 11. 增量传输与性能

要求：

- 优先使用 rsync
- 未修改文件不重复传输
- 支持块级差异传输
- 尽量减少大型聊天文件重传
- 图片和资源不重复传输
- 支持删除镜像
- 网络中断后可以安全重试
- 避免无意义的完整哈希扫描
- 根据文件类型合理选择压缩
- 合理处理 Android 存储限制
- 显示实际传输字节数
- 避免默认使用破坏一致性的原地写入策略

跨平台同步时，必须考虑：

- Windows 文件名大小写行为
- 文件权限差异
- 符号链接
- 非法文件名
- 路径长度
- 修改时间精度
- 文件锁
- 存储空间不足

请给出具体的 rsync 参数设计及理由。

## 12. 最低限度防误覆盖

我不需要复杂冲突管理，但要求以下保护：

1. 空目录不能误覆盖有效数据。
2. 危险路径不能作为同步目标。
3. VPS 未初始化时禁止直接拉取覆盖。
4. 同一时间只能进行一个冲突性的同步任务。
5. 上传失败不发布为有效状态。
6. 拉取失败不应用不完整的数据。
7. 覆盖存在未上传修改的本机数据前进行确认。
8. 保留一次必要的覆盖前恢复数据。
9. 支持预览和错误日志。
10. 同步方向必须明确。

正常同步尽可能做到一键完成。

只有异常情况才要求额外确认。

## 13. 安全设计

VPS 是私人服务器，允许保存明文的聊天和 API 密钥。

不强制实施端到端加密。

但必须：

- 使用 Tailscale 私网访问
- 使用 SSH 进行文件传输
- 使用专用低权限同步账户
- 使用可信 SSH 主机身份校验
- 正确处理 SSH 密钥
- 限制同步存储目录
- 禁止任意路径读写
- 禁止通过前端传入任意系统命令
- 禁止命令拼接注入
- 不在日志中输出密钥
- 不同步 SSH 私钥和 Tailscale 设备身份状态
- 保护插件管理 API 的身份认证和 CSRF 边界
- 同步数据只允许可信的本地设备访问

区分酒馆 API 密钥和基础设施访问凭据。

插件本身拥有较高的本地文件权限，必须进行严格输入验证和路径限制。

默认不需要增加对外开放的 HTTP 同步服务。

- 正在应用更新

**高级设置**
